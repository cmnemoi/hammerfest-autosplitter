> demarrer sans attendre le balayage, choisir le compteur du game time, et
> dater le depart en temps reel. Les reponses -- dont deux differentes de ce
> qui etait envisage ici -- sont dans
> [recap-temps-reel.md](recap-temps-reel.md).


We now have a working memory-resolution approach for Hammerfest under Pepper Flash / AVM1.

The expensive part is the initial AVM1 resolution:

* find the Pepper Flash process/module;
* scan the heap for a known interned obfuscated string;
* recover AVM1 String / property-table layout;
* find the relevant ScriptObjects;
* identify `GameManager`;
* follow `GameManager.current`;
* resolve the live `GameMode`;
* read the level and timing state.

Once `GameManager` has been found, normal polling is cheap. The main performance problem is the **initial heap scan**, which can take on the order of a second and has variable duration.

There are now three related but distinct problems to investigate:

1. Start the timer without waiting for the heap scan.
2. Decide which in-game counter should define Game Time.
3. Find an exact Real Time start timestamp independently from the slow AVM1 resolution.

---

# 1. Timer startup: remove AVM1 resolution from the critical path

We probably do **not need to finish the heap scan before starting the timer**.

The Pepper Flash process itself is created when a game session starts. Detecting process creation is cheap and effectively immediate compared with resolving the AVM1 heap.

So the architecture could be:

```text
Pepper process appears
        |
        +--> initialize/start timer immediately
        |
        +--> start AVM1 resolution
                  |
                  +--> find GameManager / GameMode
                  +--> read timing state
                  +--> synchronize timer
```

The important architectural point is:

> The heap scan should be state synchronization, not start detection.

This is especially useful for Game Time because an in-game elapsed counter can later overwrite/correct the displayed time.

## Things to investigate / implement

### Separate process detection from AVM1 resolution

The main update loop should notice the Pepper process and initialize the timer without waiting for `resolve_game_manager()` or any complete heap scan.

### Consider incremental resolution

Avoid one huge blocking scan if possible.

For example:

```text
Resolver state:
- FindWorldString
- FindStringReferences
- InferPropertyTable
- FindGameManager
- Ready
```

Each tick could perform a bounded amount of work.

This may slightly increase total resolution latency, but avoids blocking LiveSplit for hundreds of milliseconds.

### Batch remote memory reads

Check whether the current implementation performs many small `ReadProcessMemory` calls.

Prefer:

```text
read whole committed region / large chunk
        ↓
scan local buffer
        ↓
perform targeted remote reads only for candidates
```

The syscall/process-boundary cost may otherwise dominate the scan.

### Cache only within the current Pepper process

Once found:

```text
GameManager
    -> current
    -> GameMode
```

should be the fast path.

Validate the anchor before using it and fall back to complete resolution only when invalid.

The Pepper process itself is recreated between game sessions, so heap addresses cannot be reused across processes.

# 2. Game Time: investigate `duration` instead of assuming `gameChrono`

We currently have two independent timing mechanisms in the game.

## `gameChrono`

`GameMode.gameChrono` is a `Chrono`.

Its effective value is based on:

```text
frameTimer - gameTimer
```

and it is explicitly stopped by `GameMode.lock()` and resumed by `unlock()`.

Therefore:

```text
gameChrono
→ game time excluding pauses
```

This works technically, but it may not match the desired speedrun semantics.

For the intended rules, opening the pause menu should **not stop the run timer**. A pause is either discouraged, irrelevant, or potentially forbidden by the rules, so the timer should keep counting.

Therefore `gameChrono` may be the wrong counter for the final autosplitter.

---

## `duration`

The second counter is:

```text
GameMode.duration
```

which is accumulated as:

```text
duration += Timer.tmod
```

each frame, and converted to seconds using:

```text
duration / Data.SECOND

Data.SECOND = 32
```

The game itself logs this value on game over.

We already observed:

```text
duration    14815.6 / 32 = 463.0 s
gameChrono                 = 462.9 s
```

So under normal gameplay the two counters agree very closely.

This makes `duration` the main candidate for the desired Game Time.

The intended semantics would be:

```text
Game Time
= duration / 32
= game simulation time
= pause included, if Timer.tmod continues being accumulated during pause
```

This is **not intended to be Real Time**.

If the game slows down and `Timer.tmod` reflects that slowdown, that may actually be desirable for Game Time.

---

## What needs to be verified about `duration`

The most important question is:

> Does `duration += Timer.tmod` still execute while the game is paused?

The simplest runtime test:

```text
before pause:

duration   = D0
gameChrono = G0

pause for ~10 real seconds

after pause:

duration   = D1
gameChrono = G1
```

Desired result:

```text
(D1 - D0) / 32 ≈ pause duration
G1 - G0            ≈ 0
```

If that holds, `duration` is much closer to the desired Game Time semantics.

Also test:

* normal gameplay;
* pause menu;
* alt-tab / background window;
* severe slowdown or low FPS.

Not because `duration` needs to match wall-clock time, but to understand exactly what `Timer.tmod` represents.

Questions:

```text
Does Timer.tmod compensate for low FPS?

Is it clamped?

Does it represent game simulation time?

Does it continue advancing while fl_pause is true?

Can it ever move backwards or jump?
```

The goal is to characterize it as a **Game Time clock**, not as RTA.

---

# 3. Keep the three timing concepts separate

At this point we should explicitly distinguish:

```text
gameChrono
→ gameplay clock
→ pauses excluded


duration / 32
→ candidate Game Time
→ pauses ideally included
→ likely follows game simulation speed


Real Time
→ external monotonic time
→ pauses included
→ slowdown does not matter
→ must measure actual elapsed wall-clock/monotonic time
```

Do not conflate these.

`duration` may replace `gameChrono` for Game Time while `gameChrono` remains useful as a reverse-engineering cross-check.

---

# 4. Game Time startup with `duration`

If `duration` becomes the Game Time source, the startup strategy stays similar.

We can start the timer immediately on a cheap signal and synchronize later.

Example:

```text
t = 0.000
Pepper process appears
timer starts

t = 1.400
AVM1 resolution finishes

duration / 32 = 1.173 s

set_game_time(1.173 s)
```

The initial heap-scan latency does not become permanent timing error because the Game Time value is absolute.

Therefore the initial AVM1 resolution still does not need to be on the start critical path.

---

# 5. Real Time: finding the actual start timestamp

Real Time is a different problem.

For Game Time we can start approximately and correct later using an absolute in-game elapsed counter.

For Real Time we need:

```text
real_time = now - exact_start_timestamp
```

The variable heap-scan duration therefore cannot be part of the measurement.

Starting the timer when AVM1 resolution finishes is wrong.

Starting it when the Pepper process appears is cheap and deterministic from our side, but process creation likely occurs before the actual speedrun start point because Flash/SWF initialization still happens afterwards.

So we need either:

1. observe the exact start event cheaply;
2. or reconstruct its timestamp retrospectively.

---

# 6. Real Time hypothesis A — cheap external/native start signal

Best outcome:

find an observable event that happens at or very close to the actual RTA start without requiring a full AVM1 heap resolution.

Conceptually:

```text
Pepper process starts
        ↓
Flash/SWF initialization
        ↓
SOME CHEAP OBSERVABLE EVENT
        ↓
timestamp t0 immediately
```

Then:

```text
RTA = monotonic_now - t0
```

and AVM1 resolution happens afterwards.

Potential things worth investigating:

* Pepper/Flash runtime events;
* stable native state transitions;
* SWF initialization milestones;
* a native function reliably reached at the start event;
* another cheap piece of memory accessible without discovering the AVM1 object graph.

Process creation itself should not be assumed to be the correct RTA start until the desired speedrun start semantics have been defined and measured.

---

# 7. Real Time hypothesis B — reconstruct the start retrospectively

This would be ideal because it makes heap-scan performance irrelevant to timing accuracy.

Suppose AVM1 resolution finishes at local monotonic time:

```text
T
```

and at that instant we recover a Flash-side timestamp or elapsed value:

```text
E
```

If `E` tells us exactly how long ago the RTA start event occurred:

```text
start_timestamp = T - E
```

Example:

```text
AVM1 resolution finishes at local time 10.000 s

recovered elapsed value = 2.731 s

=> actual start timestamp = 7.269 s
```

The timer can immediately display the correct RTA even though the start was only discovered later.

---

# 8. `frameTimer` / `Std.getTimer()` may be useful for RTA reconstruction

`Chrono.update()` does:

```text
frameTimer = Std.getTimer()
```

and this update runs before the pause check.

Therefore `frameTimer` continues to change even while `gameChrono` itself is stopped.

This makes it interesting for RTA investigation.

Important distinction:

```text
frameTimer
!= gameChrono
```

`frameTimer` appears to represent the Flash runtime's monotonically advancing timer.

`gameChrono` derives its gameplay-time semantics from `frameTimer`, `gameTimer`, `haltedTimer`, etc.

We should investigate what exactly backs:

```text
Std.getTimer()
```

in this Pepper Flash build.

Questions:

```text
What is its zero point?

Process creation?

Flash plugin initialization?

SWF initialization?

AVM runtime initialization?

Is it monotonic?

Does it continue during pause?

Does it continue during background throttling?

How closely does it track the OS monotonic clock?
```

If we can establish a stable relationship:

```text
our monotonic clock <-> Flash Std.getTimer()
```

then a Flash-side event timestamp might be convertible into an exact local RTA start timestamp.

---

# 9. Determine the exact timing lifecycle

Before optimizing the heap scanner aggressively, trace the timing lifecycle from source and runtime.

Specifically:

```text
Pepper process creation
SWF loading
GameManager creation
GameMode construction
Chrono construction
Chrono.start()
gameTimer initialization
Chrono.update()
frameTimer = Std.getTimer()

duration initialization
duration += Timer.tmod

level 0 initialization
intro/loading sequence
first playable frame
```

For each event determine:

```text
1. Flash timestamp/state
2. duration value
3. gameChrono value
4. frameTimer value
5. relation to the intended Game Time start
6. relation to the intended RTA start
7. whether its timestamp can be recovered later
```

---

# 10. Real Time hypothesis C — hook a native function

If no cheap observable state or retrospective clock mapping exists, a native hook is another possible approach.

Conceptually:

```text
interesting function in pepflashplayer.dll
        ↓
hook
        ↓
monotonic timestamp
        ↓
exact RTA start
```

This avoids heap scanning for start detection.

However, treat this as a later option because it introduces much more complexity:

* native function identification;
* signatures / offsets;
* version dependence;
* injection or instrumentation;
* trampoline/hooking machinery;
* likely OS-specific implementations;
* significantly worse cross-platform support.

Do not jump to hooking until the clock-reconstruction approach has been investigated properly.

---

# 11. Target architecture

Ideally the final timing model looks like:

```text
                 process lifecycle
                       |
                       +------> initialize timer ASAP
                       |
                       v
                AVM1 resolver
                       |
          +------------+-------------+
          |                          |
          v                          v
      duration                    level state
          |                          |
          v                          v
      Game Time                    splits


OS monotonic clock
        ^
        |
Flash runtime timing / start-event reconstruction
        |
        v
    Real Time
```

The three responsibilities stay independent:

```text
STARTUP
→ do not wait for heap scan

GAME TIME
→ probably duration / 32
→ pause should remain counted
→ slowdown may legitimately affect it

REAL TIME
→ OS monotonic elapsed time
→ independent from slowdown and pause
→ exact start timestamp must be observed or reconstructed
```

# Suggested next work

Priority order:

1. Verify whether `duration` continues advancing during pause.
2. Characterize `Timer.tmod` under pause, slowdown and background throttling.
3. Separate timer initialization from full AVM1 resolution.
4. Measure `frameTimer`, `gameChrono`, `duration` and local monotonic time simultaneously.
5. Trace the initialization of `Chrono`, `gameTimer`, `duration` and the first playable frame.
6. Determine whether the RTA start timestamp can be reconstructed retrospectively from Flash timing state.
7. Only after that, consider native hooking if reconstruction proves impossible.

The key idea is still:

> Do not optimize the heap scan as if making it instantaneous were necessarily the solution.

For both Game Time and Real Time, the better solution may be to make timing **independent of when AVM1 resolution completes**.
